# 方針書: リポジトリ公開整理・ドキュメント再編・テスト正式化

作成: 2026-08-05。この文書は**チームコンテナ側で作業するエージェントへの実行指示書**である。
本リポジトリ(scorelib)をチーム内公開に堪える状態へ整理し、テストデータと正解検証を
正式化するための方針をまとめる。**実行完了後、本ファイル自体も §1 の local/ へ移動する。**

## 0. 実行者への前提

- 作業ルールはリポジトリの CLAUDE.md と `.claude/rules/` に従う(テスト全パス・
  ドキュメント追随・バージョン判断の Definition of Done。旧 AGENTS.md は廃止し
  この2つへ統合済み)。ルールファイル自体の扱いはチーム側で解決済みのため
  本方針書の対象外。
- **各フェーズの完了時点で必ず全テストがパスしている**こと(main を緑に保つ。
  大きいフェーズは feature ブランチで)。
- git 履歴の書き換えはしない(過去に削除したファイルが履歴に残るのは許容済み)。
- 本方針書内の「local/」= リポジトリ直下に新設する .gitignore 済みディレクトリ。
  git 管理から外すだけでファイルは手元に残す(削除ではなく `git rm --cached` +移動)。
- 判断に迷う点・本方針書と実態が食い違う点は、勝手に解釈せずユーザーに確認する。
  特に §5 の「要確認事項」は着手前に確認すること。

## 3. フェーズ3: テストデータの正式化(実験種類ごとのミニ実測データ)

### 3-1. 背景と設計判断

- 現在の `tests/data/result_tmp_mini/` は実データからその場その場で抽出してきたもので、
  全7 type(FBC/KLD/PROGLOOP/PROGSTATUS/dVthSGWLD/tPROG/tR)が揃った
  「スーパーセット」になっている。
- しかし実際の実験は種類ごとに出力ファイル構成が違う(**Read 系では KLD が出ない、
  Boost 系では tR が出ない**、等)。ファイル欠落そのものがエンジンの仕様対象
  (vthSkip・introspect の type 検出・UI 候補)なので、**データセットは実験種類ごとに
  分ける**(ひとまとめのスーパーセットにしない)。今後実験種類が増えても
  ディレクトリ追加だけで済む構造にする。

### 3-2. 構成

```
tests/data/
  read_mini/       # Read系実験の実測抜粋(実際の出力ファイル構成そのまま。KLD無し)
  boost_mini/      # Boost系(データ入手でき次第。tR無し)
  datasets.py など # データセットレジストリ(下記)
```

- **レジストリ(マニフェスト)**: データセットごとに「種類名 / 含まれる type /
  元データの由来(実験の識別情報) / 生成コマンド」を1箇所に登録し、conftest は
  ここからパラメータ化 fixture を作る。**テスト側に type 一覧をハードコードしない**
  (現 `ALL_MINI_TYPES` のような定数はレジストリ参照へ置き換える)。
  形式は実装時に判断してよい(Python 定数 dict で十分)。
- **ダミーデータ(Board/Chip 拡張)は別データとして持たない**: 既存どおり
  `make_pseudo_dummy` で実測ミニから生成する(一源管理)。
- **テスト config も正式化の対象**: 現在の `tests/fixtures/config.jsonc` は
  その場その場の抽出で作られた暫定物。データセットごとに**実際の実験で使われた
  config を基にした正式なテスト config** を対で用意する(§4-3 の正解値生成に使う
  config と揃えるのが望ましい)。暫定 config への参照が無くなった時点で置き換え・
  削除する(§3-4 の移行方針と同じ進め方)。

### 3-3. 抜粋の作り方(抽出スクリプト)

- `scripts/make_test_excerpt.py`(新規)を作り、リポジトリにコミットする。
  実測フルデータのディレクトリから、指定した軸範囲(WL・Block・epoch 等)で
  **決定的に**間引いた抜粋を出力する。
- **形式は一切変換しない**(このリポジトリの確立済み教訓): ヘッダの有無・列順・
  ファイル名・csv/csv.gz の別を元のまま保存する。map 系・parameterLabel 系・
  initial_temperature 等の付帯ファイルも実機構成のまま含める。
  ファイル種類はハードコードせず、introspect と同じ「中身の形」で扱う
  (今後ファイル種類が増えても抽出スクリプトが壊れないように)。
- サイズ目安: 1データセット数百 KB 以内・各 csv 数百行程度。集計・相対化・
  WLgroup が意味を持つ程度の軸の広がり(複数 WL・複数 State・Override/Measure
  両側の測定を含む)は確保する。
- 実測フルデータは**チームコンテナ側にのみ存在し、リポジトリに入れない**(既存 .gitignore
  の `/result_tmp*` 方針を維持)。抜粋の生成コマンド(引数込み)をレジストリに
  記録し、再生成可能にする。

### 3-4. 移行方針(ビッグバンで置き換えない)

1. まず `read_mini/` を追加し、レジストリと fixture 基盤を作る。
2. 既存テストを順次 `read_mini/`(+ダミー導出)へ移行する。**KLD 等 Read 系に
   存在しない type に依存するテスト(vthSkip 等)は、該当 type を含む実験種類の
   データセット(Boost 系等)が入るまで既存 `result_tmp_mini` のまま残してよい**。
3. どのテストがどのデータセットに依存するかの対応表を移行中は本方針書(または
   local/ の作業ノート)に維持し、`result_tmp_mini` への参照が無くなった時点で削除する。
4. 全種類に共通で成り立つべき性質(introspect の type 検出・軸カタログ・UI 候補等)は、
   レジストリ全データセットに対するパラメータ化テストにする。

### 3-5. 実験種類を将来追加するときの手順(この構造のゴール)

1. チームコンテナ側で `make_test_excerpt.py` により新種類の抜粋を生成 → `tests/data/<種類>_mini/` に追加
2. レジストリに1エントリ追加(種類名・type 一覧・由来・生成コマンド)
3. その種類の実 config で §4 の正解値を生成してコミット
4. パラメータ化テストが自動で新データセットを回ることを確認、種類固有の仕様
   (出ないファイル・固有 type)があれば個別テストを追加
5. ドキュメント追随(テスト一覧・CHANGELOG)

## 4. フェーズ4: 正解値(ゴールデン)テスト — 「現行と同じ答えか」の検証

### 4-1. 背景

現状のテストは「手計算との照合」「テスト内の素朴な別実装との照合」
「現行スクリプトとの照合(ただし expand_FBC_measure の軸展開のみ)」の3層で、
**最終スコア値が現行の本番スコアスクリプトと一致することの検証が存在しない**。
これを埋めるのが本フェーズの目的であり、全フェーズ中で最も価値が高い。

### 4-2. 現行スコアスクリプトの参照コピー

- チーム内にある現行のスコア計算スクリプト(pandas でデータフレームを手動操作する
  Python プログラム)を `reference_scripts/` へ参照コピーとして置く
  (expand_FBC_measure.py と同じ位置づけ)。
- **原則無改変**。今の環境(Python 3.13 等)で動かすための最小限の修正が必要な
  場合のみ、修正箇所に日付つきコメントを残す。計算ロジックには触れない。

### 4-3. 正解値の生成とテスト(推奨方式: 正解値をコミットし、CI は値と比較)

1. 抜粋データセット(read_mini 等)+ **実際の実験で使われた config** に対して
   現行スクリプトを実行し、スコア値(パーツ別・合成後)を
   `tests/data/<種類>_mini/expected_scores.json` 等としてコミットする。
   生成に使ったコマンド・スクリプトの版もファイル内に記録する。
2. テストはエンジン(`compute_score_file`)の結果をこの正解値と比較する。
   これにより **CI は pandas にも旧 Python にも依存しない**(pandas をエンジンの
   依存に混ぜない。正解生成を pytest 内で毎回行う方式は採らない)。
3. 許容誤差: まず厳しく(相対誤差 1e-12 程度)始め、pandas/polars の演算順序差等で
   必要になった場合のみ緩め、緩めた理由をテスト内コメントに記録する。
4. 現行スクリプトが対応していない機能(本エンジンで追加された op 等)は対象外で
   よい。**現行スクリプトが計算できる範囲の config で全パーツ一致**が目標。

### 4-4. チームコンテナ専用フル検証テスト(コミットしない実データでの全量照合)

- `tests/test_realdata_validation.py`(新規)を作る。環境変数(例:
  `SCORELIB_REALDATA_DIR`)で実測フルデータ+実 config +**実測時に本番側が
  算出したスコア値**の置き場を指すときのみ実行し、**未設定なら自動 skip**
  (CI・他メンバの環境を壊さない)。
- 内容: エンジンで全量計算し、本番側が実際に出したスコア値と照合する。
  抜粋では拾えない規模・値域での一致確認が目的。
- 実データの置き場・skip 条件はテスト一覧ドキュメントに明記する。

## 5. 要確認事項(着手前にユーザーへ確認)

1. 現在の `result_tmp_mini` の元になった実験はどの種類か(KLD と tR が両方含まれて
   おり、Read 系/Boost 系のどちらの構成とも一致しない。歴代の抽出の混成である
   可能性が高い)。→ read_mini の元にする実験データの指定をもらう。
2. 正解値生成に使う「実際の実験で使われた config」はどれか。現行スクリプトが
   計算した(または再計算できる)スコア値と対で入手できるか。
3. 現行スコアスクリプトのファイル名・置き場所と、実行方法(引数・前提ディレクトリ構成)。
4. Boost 系データの入手時期(§3-4 の移行完了とKLD 依存テストの置き換えはこれ待ち)。

- 順序: フェーズ1→2 は実データ不要で先行できる。フェーズ3→4 は実データ・
