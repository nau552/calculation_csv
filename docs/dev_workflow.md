# 開発運用ガイド（git・CI に馴染みのない開発者向け）

2026-07-28 に導入した開発運用の仕組みの解説。**手順の正は
[`../README.md`](../README.md) の「開発の進め方」「リリース手順」**で、
このガイドは「それぞれが何者で、なぜあるのか」を説明する（testing_guide.md の
git 運用版）。

## 全体像 — 何のためにあるのか

やりたいことは3つだけ:

1. **main ブランチを常に「テスト全パス・いつでも SVN 同期できる」状態に保つ**
2. **「どのコードを出荷したか」を後から特定できるようにする**（タグ・CHANGELOG）
3. **テストの実行を人の記憶に頼らず自動化する**（フック・CI）

以下の各ファイルはすべてこの3つのどれかに対応する。

## 各ファイル・ディレクトリの正体

### `scripts/hooks/` と `pre-push` — git フック

**git フック**とは「git の特定の操作の直前/直後に自動実行されるスクリプト」。
`pre-push` は **push の直前**に走り、スクリプトが失敗（exit 非0）すると
**push 自体が中止される**。中身は pytest の全実行 —
つまり「テストが落ちる状態のコードは push できない」を物理的に保証する保険。

- 実行に使う python は `.venv`（Windows/Unix）→ PATH 上の `python3`/`python`
  の順で「pytest が import できるもの」を探す（docker / devcontainer 等、
  依存がシステム python に入っている環境でも動くように — 2026-07-29）
- 見つからなければ **push を中止する（fail-closed）**: 社内環境では CI が
  未整備の期間があり、フックが唯一の自動テスト実行になりうるため、黙って
  スキップして CI に委ねる旧挙動をやめた。環境を作れないマシンから意図的に
  push する場合は `git push --no-verify`

- フックは通常 `.git/hooks/`（git 管理外）に置くものだが、それだとリポジトリを
  clone し直すと消える。そこでリポジトリ管理内の `scripts/hooks/` に置き、
  `git config core.hooksPath scripts/hooks` で「フックはここを見ろ」と設定する
  （**clone したマシンごとに1回この設定が必要**）
- 緊急時は `git push --no-verify` でスキップできるが、CI が同じテストで
  落ちるだけなので基本使わない

### `.gitattributes` — ファイルごとの git の扱いの指定

git はテキストファイルの**改行コード**を OS に合わせて自動変換する
（Windows では checkout 時に LF → CRLF）。普段は便利だが、**シェルスクリプトは
CRLF だと実行時に壊れる**（`\r` が命令の一部として解釈される）。
`.gitattributes` の `scripts/hooks/* text eol=lf` は「この場所のファイルは
常に LF のままにしろ」という指定で、フックが Windows で checkout されても
壊れないようにしている。それ以外の用途では今のところ使っていない。

### `ruff.toml` — コード規約（lint・整形）

**ruff** は Python の lint（問題のある書き方の検出）と整形を行うツール。
このリポジトリのコードはチームの最適化スクリプト群に組み込まれるため、
規約は**チーム共通コンテナの `.devcontainer/ruff.toml` に合わせる**
（2026-07-31 に転記して全体を警告ゼロ化。リポジトリ独自の規約は作らない）。

**2026-08-05 に設定の置き方を再構成した。** チームコンテナの実際の配線
（下記「なぜ」参照）に合わせ、「免除は設定でなくファイル自身が持つ」形にした:

- **`.devcontainer/ruff.toml`** — チーム原本の転記（無改変で置く。チーム内
  リポジトリと同じ配置なので、コンテナの /check（`--config
  .devcontainer/ruff.toml` で起動と確認）がこのリポジトリでもそのまま動く）
- **直下の `ruff.toml`** — scorelib 所有の薄い配線。`extend` でチーム設定を
  継承するだけで、**免除は書かない**。例外は2つだけ（ファイル内コメントで
  代替できない技術的な補正。詳細は同ファイルのコメント）:
  - チーム設定の `tests/*` 免除の再掲 — per-file-ignores のパターンは
    「定義した設定ファイルのあるディレクトリ」基準で解決されるため、
    extend 経由では `.devcontainer/tests/*` の意味になり効かない
    （実測 2026-08-05。/check の `--config` 直指定では原本のまま効く）
  - `ruff.toml` 自身への RUF201（セレクタをコードでなく名前で書け）の
    自己参照免除 — セレクタの名前表記は素の（`--preview` 無し）ruff が
    **設定ごと読めなくなる**（致命エラー。実測 2026-08-05）ため、
    コード表記のまま容認する
- **免除は各ファイル内の抑止コメント**に理由つきで置く。書式は2種類:
  - ファイル単位（そのファイルではカテゴリとして意図的なもの。
    Copyright 行の直後に置く）: `# ruff: file-ignore[ルール名] 理由`
  - 行単位（単発の意図的な例外）: `# ruff: ignore[ルール名] 理由`
  - いずれも**ルール名表記**で書く（preview の RUF106 が求める形。
    旧コード表記の抑止 73 件は 2026-08-05 に `--fix` で一括変換した）

**なぜファイル内コメントに一本化したか**（2026-08-05 にチーム環境を確認）:
チームコンテナのエディタは settings.json の `ruff.configuration` が、/check は
`--config` が、どちらも**チーム設定だけ**を読み、リポジトリ側の toml は
読まない。つまり toml に書いた免除はチーム内では一切効かず、実際に
`batch/__init__.py` の RUF067 警告がコンテナのエディタに表示されていた。
ファイルに同居する抑止コメントだけが、どの環境（コンテナのエディタ・
/check・CI・手元）でも同じに効く。

- ローカルでの実行: `.venv/bin/ruff check . --preview`（lint）と
  `.venv/bin/ruff format .`（整形。Windows は `.venv/Scripts/`）。
  CI でも同じ2つを検査するので、push 前に流しておくと差し戻しがない
- **検査は `--preview` 一本**（2026-08-05 に一本化）: チームの運用はエディタ
  （preview 有効）も /check（`--preview` 付きと確認）も preview で統一されて
  おり、素の実行はチーム内のどこにも登場しない。抑止コメントのルール名表記は
  素の実行では解釈されない（RUF102）ため、素の実行は検査しない
  （2026-07-31〜08-04 の「コード表記 + 両モードゼロ」運用は、/check にも
  `--preview` が付いていると確認できたため終了。当時コード表記を選んだ理由も
  同じ制約の裏返しだった）
- ruff の**版は dev extras で 0.16.0 に固定**している（チームコンテナの ruff も
  同版であることを確認済み — 2026-07-31）。版が動くと有効ルールが変わり
  「警告ゼロ」の状態が崩れるため。上げるときは全体を再検査してから

#### 品質向上パスの進め方（免除・noqa を将来どう減らすか）

ruff.toml の固有節と行単位 noqa は「直すこと自体が目的に反する」既存コードの
容認であり、**将来の品質向上作業の作業リスト**でもある（noqa の理由コメントが
そのまま「何を・なぜ見送ったか」の記録になっている）。減らすときの方針
（2026-07-31 合意）:

1. **正しく動くことが最優先**。品質向上は動作を維持しながら段階的に行う。
   一括リファクタはせず、独立した依頼（feature ブランチ）として計画してから
2. **ラチェット方式**: per-file-ignores はディレクトリ単位でなくファイル単位
   でも書けるので、「直したファイルから免除リストを外す」形で狭めていく。
   免除が残っている場所 = 未着手の作業リスト、という管理になる
3. **順序は「引数の束ね直し → 関数分割」**。引数が多い関数（PLR0913/0917）は
   関連する引数を dataclass 等に束ねる定型作業でリスクが小さく、どの引数群が
   一緒に動くかが後の分割単位の材料になる。関数の分割（C901/PLR0912/0915、
   preview 追随で加わった PLR0914=ローカル変数数・PLW0717=try 節の文数も同類）
   はロジックの再構成なので後回し
4. **UI の分割をやる前に AppTest を厚くする**。分割はテストが挙動を固定して
   いて初めて安全（エンジン側はテストが厚いので先に着手できる）
5. **キーワード専用化（FBT 系の noqa）や例外型の変更（TRY004）など
   「呼び出し側・挙動が変わる」修正も同パスで扱う**（現状は理由付き noqa で
   見送り中）

**2026-07-31 追記: 品質向上パスを実施した**（feature/quality-pass）。結果:

- 関数サイズ系の違反 96 件 → 10 件（すべて意図して残す設計判断）。上記 3 の
  順序どおり「引数の束ね直し → 関数分割」で、エンジン → scripts → UI
  （AppTest を 19 本増強してから）の順に実施。数値結果・エラー文言・画面文言は
  不変（305 → 324 テストで固定）
- **公開 API（compute_score_part / compute_score_file / compute_dummy_part /
  apply_dvtbudget / BatchRunner / ブリッジ見本2関数）は dataclass に束ねず、
  省略可能引数のキーワード専用化（`*,`）まで**とした。組み込み側（SVN・
  ブリッジ）の呼び出し互換を壊してまで束ねる利得がないため。総引数数
  （PLR0913）だけが残り、**該当する関数の def 行の行単位抑止**に理由つきで
  記録（2026-07-31 にファイル単位免除から移行 — 同じファイルの新しい関数へ
  免除が及ばないように）。内部関数・UI は実際に束ねた（_BatchInputs /
  EditorContext / LoadInputs / TestComputeInputs 等）
- 見送っていた FBT 系（キーワード専用化）と TRY004（型検査の ValueError →
  TypeError。custom 関数不在・世代情報 json・import_score_file の3箇所）、
  TRY301（raise のヘルパー抽出）も同時に解消。行単位の関数サイズ系・FBT・
  TRY の抑止コメントは 0 件になった
- 残る意図的な容認: PLR0911（isinstance 早期 return を連ねる型変換関数が
  最も読みやすい）、ui/* の BLE001・PLC0415、ui/state.py の PLR6104、
  ui/widgets.py の B909（いずれも設計。ruff.toml の理由コメント参照）

**2026-08-05 追記: 免除の置き場所をファイル内コメントへ移行し、追加の修正を
実施した**（設定再構成と同時。上記「ruff.toml」節参照）。結果:

- toml の免除節は全廃し、各ファイル先頭の `# ruff: file-ignore[...]` と
  行単位の `# ruff: ignore[...]` へ理由ごと移設。**ラチェット方式の作業リスト
  も「file-ignore ヘッダが残るファイル」に読み替える**（直したファイルから
  ヘッダの該当ルールを外していく）
- 同時に「実害なく直せる」20 件を解消: 未使用の fixture 引数（ARG001 ×9 —
  値を使わないテストの引数から削除）、monkeypatch スタブのラムダ引数
  （ARG005 ×4 — `_` 付きへ改名）、bool の位置渡し（FBT003 ×4 — キーワード
  引数化）、ループ中の削除（B909 ×2 — 複製を反復）、非累算代入
  （PLR6104 ×1 — 新リスト作成の意図を保つ `[*x, y]` 形式へ）。これにより
  上記 2026-07-31 時点の容認リストのうち ui/state.py の PLR6104 と
  ui/widgets.py の B909 は解消済み
- テスト 339 件・ruff（preview）・format・pyright すべてゼロを確認

### 型チェック（Pylance / pyright）

**Pylance** はコンテナの VS Code が使う型チェッカーで、その中身の CLI 版が
**pyright**。チームの水準は「**Pylance の警告が出ないコードを書く**」
（設定で黙らせない — 2026-07-31 確認）で、このリポジトリもそれに合わせて
全体をゼロ化した（当初 416 件 → 0。抑止コメント・設定による無効化は不使用。
型注釈の精密化・TypedDict・cast と、到達しないパスへの防御チェック数箇所で解消）。

- ローカルでの実行: `.venv/bin/pyright scorelib_param ui tests scripts
  reference_scripts`（Windows は `.venv/Scripts/`）。CI でも同じ検査が走る
- **版は dev extras で 1.1.411 に固定**（ruff と同じ理由: 版が動くと検出が
  変わり「ゼロ」の状態が崩れる。上げるときは全体を再検査してから）
- エディタ（Pylance）は開いているファイルしか検査しないので、全体の確認は
  CLI か CI で行う

### `CHANGELOG.md` — 版数ごとの変更履歴

「エンジンを 0.4.0 から 0.5.1 に上げると何が変わるのか」に答える文書。
読者は**SVN 側でエンジンを使う人**（自分含む）。開発の時系列メモ
（docs/score_gui_progress.md）との違いは、**版数を軸に「追加/変更/互換性」だけを
整理してある**こと。版を上げたら必ず追記する（リリース手順の一部）。

### `.github/workflows/test.yml` — GitHub Actions（CI）

**CI（継続的インテグレーション）**とは「リポジトリに変更が届くたび、クリーンな
環境で自動的にテストを走らせる仕組み」。GitHub Actions は GitHub 内蔵の CI で、
`.github/workflows/` に置いた yaml が設定ファイル。

- push または Pull Request のたびに、GitHub のサーバが Ubuntu 上で
  **本番エンジン環境と同じ Python 3.13** で `pip install → ruff（lint・整形
  検査）→ pytest` を実行する（ruff は 2026-07-31 に追加）
  （2026-07-28 に開発機も 3.13 へ移行したため単一バージョン。旧環境の
  サポートが必要になったら matrix にバージョンを足す）
- 結果は GitHub リポジトリページの **Actions タブ**で見る（✓ green / ✗ red）。
  ローカルで通っても CI で落ちることがある（venv に偶然入っていたものへの依存、
  OS 差など）— それを検出するのが目的
- ローカルの pre-push フックと役割が重なるが、フックは「push 前の即時の保険」、
  CI は「独立環境での事後検証+記録」で補完関係

### タグ（`ver.X.Y.Z` と `ui-YYYYMMDD` の2系統）

タグは「このコミットがリリースだった」という**動かない印**。ブランチと違って
後から進まない。系統は2つ:

- **`ver.X.Y.Z`** = エンジンのリリース。`scorelib_param/__init__.py` の
  `__version__` と常に一致し、SVN 同期はこのタグから行う。
  **SVN 側で動いているエンジンの版数 → git のコード**を特定する用途
  （版ズレ調査・ロールバックは `git checkout ver.0.5.1`）が本命
- **`ui-YYYYMMDD`** = UI のみのリリース（日付ベース・番号なし）。UI サーバへの
  配布はこのタグ（または最新の ver.*）から行う。**エンジン版数は動かさない**:
  版数は UIサイドバー・CLI ログ・SVN 内コードの全部に表示されるため、UI の
  都合で上がると SVN を共同開発する他の開発者に「SVN が古い?」という偽の
  不一致を見せてしまう。番号の意味を「エンジン版」一本に保つための分離

## 日々の開発フロー

- **小さな修正・ドキュメント**: main に直接コミットしてよい。
  ただしコミット前にテスト全パス（AGENTS.md の「変更完了の定義」）
- **数日がかりの機能**（途中状態が main に乗ると困るもの）:

  ```
  git switch -c feature/pair-suggestion   # ブランチを切って作業
  ...（コミットを重ねる）...
  # テスト全パスを確認してから
  git switch main
  git merge feature/pair-suggestion
  git branch -d feature/pair-suggestion
  ```

- push すると pre-push フック（ローカル）→ GitHub Actions（サーバ）の
  2段でテストが走る

## リリース（SVN 同期）

手順は README「リリース手順」を参照。要点は
**「テスト green → 版上げ → CHANGELOG 追記 → コミット → タグ →
`git push --follow-tags` → タグの状態から SVN 同期」**の順を崩さないこと。
こうすると「SVN にあるエンジン = タグ = CHANGELOG の該当節」が常に一対一になる。

## 社内 GitLab での CI（実運用先）

実運用は社内 GitLab。**運用の考え方（ブランチ・タグ・フック・CHANGELOG・
リリース手順）はプラットフォーム非依存でそのまま使える**が、CI の設定ファイル
だけは別物になる:

- `.github/workflows/test.yml` は GitHub Actions 専用で GitLab は読まない。
  GitLab 用は**リポジトリ直下の `.gitlab-ci.yml`**（同じ内容の下書きを作成済み。
  両ファイルは共存でき、各プラットフォームは自分のぶんだけを読む）
- Pull Request は GitLab では **Merge Request（MR）** と呼ぶ。使い方は同じ

### 社内環境で実地確認が必要なこと（机上では判断できない）

GitLab CI は yaml を置くだけでは動かず、**Runner（ジョブを実行するマシン）が
登録されていて、必要なものに手が届く**必要がある。初回パイプラインを回して、
以下のどこで止まるかを順に確認する（`.gitlab-ci.yml` の TODO と対応）:

1. **Runner の有無と種類**: Settings → CI/CD → Runners に利用可能な Runner が
   いるか。docker executor か shell executor かで yaml の書き方が変わる
2. **Docker イメージの取得可否**: `python:3.13` を Docker Hub から引けるか。
   閉域網では社内レジストリのミラー経由になることが多く、イメージ名の指定が変わる
3. **pip が PyPI に届くか**: 外に出られない環境では社内 PyPI ミラーの URL
   （`PIP_INDEX_URL`）指定が必要。**社内 CI の一番典型的なつまずきどころ**
4. **main の保護設定**: GitLab は既定で main が protected branch。権限によっては
   直 push が弾かれるため、「小さな修正は main 直コミット」運用を続けるなら
   自分のロールで push できるか確認する（または「すべて MR 経由」に寄せる）
5. **Python の用意**: shell executor の場合は Runner マシンに入っている
   Python しか使えない（3.13 があるか確認）

止まった箇所のエラーメッセージが分かれば、yaml の該当 TODO を埋めるだけで
直ることがほとんど。

## FAQ・つまずきどころ

- **PowerShell で `&&` が使えない**: `git push && git push --tags` は bash の
  書き方。PowerShell 5.1 では `git push --follow-tags` の1コマンドを使う
  （コミットと注釈付きタグをまとめて push する）
- **clone し直したらフックが動かない**: `git config core.hooksPath scripts/hooks`
  を1回実行する（README セットアップ参照）
- **CI が落ちた**: Actions タブ → 落ちたジョブ → ログで pytest の失敗箇所を
  確認。ローカルで再現・修正して push し直せばよい（main が落ちた状態を
  放置しないことだけ守る）
- **タグを打ち間違えた**: push 前なら `git tag -d ver.X.Y.Z` で消してやり直し。
  push 済みタグの打ち直しは混乱のもとなので、新しい版数で打ち直す
