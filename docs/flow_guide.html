scorelib 処理フロー図解

「どこから何が呼ばれて、どういう処理が行われるか」を、代表的な13ケースの図で追う資料です。図中の各箱に関数名とソースの位置(ファイル名:行番号)を入れてあります。行番号は 2026-07-31 時点(ver.0.7.1 + 同日の未リリース修正、main ブランチ)のものです。

リポジトリ同梱版についての注記 図の描画ライブラリ(mermaid)は docs/assets/mermaid.min.js として同梱しています。ネット接続なしで、エクスプローラーからのダブルクリックだけで図まで表示されます。

全体アーキテクチャ

リポジトリは大きく3層です。エンジン(scorelib_param/)が検証と計算のすべてを持ち、UI(ui/)はエンジンを import して呼ぶ薄いラッパー、バッチ(scorelib_param/batch/)は同じエンジンで過去実験の epoch 群を一括計算します。本番の最適化スクリプト(python3.7)からは、どちらもサブプロセスとして起動されます。

1パーツの計算の骨格(全ケース共通) {type}.csv を読む → 必要な軸だけラベル・map csv を結合 → グループ派生列を作る → order のステップを上から順に適用(相対化 → dVtBudget変換 → 軸の集計...) → 全軸を潰し切って1スカラー。全パーツの値を expression で合成したものが Score です。
ENGINE

ケース1: CLI 単発計算(本番の1 epoch 分)

本番の最適化ループが毎 epoch 呼ぶ形です。python -m scorelib_param.cli --config ... --data-dir ... を実行すると、stdout に結果 JSON が1つだけ出ます(版数表示や警告はすべて stderr)。

ケース1b: compute_score_file の内部(パーツのループ)

ここが「全パーツを計算して Score を合成する」中心です。パーツ計算のエラーは全パーツ分を集めてからまとめて例外で落とします(1件ならその例外をそのまま、複数なら「N score parts failed:」)。失敗が1件でもあれば値は返しません。

設定の検証タイミング pydantic の検証(models.py)は load_run_config の model_validate で計算前に全部走ります。WLgroup 系キー(実験スクリプト形式)の groupDefs / weightSets への取り込み(before validator)と、op ごとの形状検査(after validator)もここ。選択セットの ref だけは例外で、パーツ計算の直前に resolve_selection_refs() models.py:564 が中身へ展開し、展開後にもう一度 model_validate します(インライン記述と同じ検査を通すため)。
ENGINE

ケース2: 1パーツの計算パイプライン(compute_score_part)

エンジンの心臓部です。order のステップを上から順に適用し、全軸を潰し切って1スカラーにします。途中に「前絞り」(可換な filter の先頭前出し)と「共有キャッシュ」(相対化・dVtBudget 直後の中間結果をパーツ間で使い回す)の2つの最適化が入りますが、結果は最適化なしと同一になるよう設計されています。

共有キャッシュ(SharedComputeContext)の仕組み

  • csv 解決キャッシュ: 生成時 cli.py:558 に custom 以外の全パーツの必要軸の和集合を type ごとに前計算し、resolved(type) が初回だけ csv を読んでメモ化。各パーツは自分の必要列だけ再射影して使うので、単独読み込みと同じ列構成になります(正しさの要)。
  • prefix キャッシュ: キャッシュ点は __relative__ / __dvtbudget__ の直後だけ cli.py:766。キーには type・必要軸・グループ定義の中身・前絞りの内容・そこまでのステップ内容(JSON化)がすべて入るので、設定が少しでも違うパーツ同士は共有されません。

order に書かない軸の扱い

各集計ステップは「値列と、いま潰す軸」以外の残っている全列をキーにして group_by します(apply_aggregations aggregate.py:315)。order に書かない軸は列として残り続けるので、毎回このキーに入り、集計の次元として保たれます。グループ派生列やバッチの Epoch 列が勝手に潰れないのも同じ理由です。

ケース4: csv の読み込みと結合(axis_resolve)

全展開(FBC_expanded.csv 相当)は作らず、パーツが言及した軸のぶんだけ付随ファイルを lazy join します。結合キーは常に JOIN_KEYS = (InBatchEpoch, Board, Chip, Block, Measure) axis_resolve.py:35 です。

UI の値候補・type 検出(introspect.py)も同じデータを見ますが、こちらは「実データに存在する値だけ」を候補に出す(map 順)、「値列を持つ csv だけを type と認める」など、設計時に安全な選択肢だけを見せるためのロジックが足されています introspect.py:47 / 151 / 228。

ENGINE

ケース5: custom パーツ(自作 Python 関数)

集計パイプラインで書けない計算は、リポジトリ直下 custom_parts.py の関数を type="custom" のパーツとして呼びます。ファイル位置が固定なのは、実験入力(config)から任意コードを実行させないためです。

custom パーツは共有キャッシュの対象外で、バッチの identity_axes とも併用できません(バッチでは epoch ごとのループで呼ばれます)。

ENGINE

ケース6: vthSkip ダミー計算(測定ファイルが無い epoch)

vthSkip 中の epoch には KLD / dVthSGWLD の測定ファイルがありません。config の optimization.vthSkip にダミー値があると、該当 type のファイルが無いパーツだけ compute_dummy_part cli.py:376 で計算されます(stderr に note が出ます)。トリガーはファイル不在で、vthSkip.epochs はエンジンでは参照されません。

UI の雛形が重みを「集計時重み」で持つ理由 KLD 雛形の SGWLD 重み 0.1 は変換ステップではなく集計時重み(spec.weight)です。変換ステップはダミー計算でスキップされるため、集計時重みにしておくとダミー計算でも同じ重みが掛かります state.py:182。
ENGINE

ケース7: 計算エラー時の診断(2026-07-31 の新機構)

最終結果が null / NaN のとき、以前は「filter が0行にマッチしたのでは」という推測文言でした。現在はエラー時だけパイプラインを歩き直し、原因ステップを名指しします(成功時のコストはゼロ)。

ケース12: バッチ一括計算(過去実験データ)

python -m scorelib_param.batch --config ... --history ... --out scores.csv。複数の result_history(過去実験の epoch 群)を受け取り、識別列 Epoch を通してバッチ単位に一括計算します。単一 epoch 計算と数値等価(テストで保証)。

compute_score_batch の内部と自動フォールバック

「Epoch ごとに1行」が成り立つ理由はケース2「order に書かない軸の扱い」と同じです: Epoch 列は order のどのステップでも潰されないので、常にグループキーとして生き残ります。

ケース13: 最適化フローからの呼ばれ方(ブリッジ2種)

現行の最適化スクリプト(python3.7)はエンジンを import できないため、サブプロセス起動のブリッジを scripts/ に実装例として置いてあります。どちらも py3.7 互換・scorelib 非依存で、そのままコピーして使えます。

config はファイルパス渡しが正 現行の config ローダは読み込み時に WLgroupWeight 等を pandas Series へ加工するため、dict を渡す経路は「json 化できる形に戻せる範囲」しか対応しません(範囲展開など逆変換不能な加工は不可)。元ファイルのパスを渡すのが正、と両ブリッジの docstring に明記されています。

付録: 調査で見つかった注意点(2026-07-31 に修正済み)

この資料を作るためにコードを網羅的に読んだ際に見つかった潜在不具合とドキュメントの追随漏れです。すべて同日に修正済み(テスト5本追加・全342件パス。エンジン側の2件は CHANGELOG「未リリース」節に記録、版上げは次リリース時)。図中の行番号は修正後のコードに合わせてあります。

修正した潜在不具合

  • 画面2「雛形を再生成」の例外画面: 「⚠ データ無し」の type のパーツで押すと KeyError になっていた → カタログ(custom は関数一覧)の無い type ではボタンを無効化 app.py:1174-1183。他 type のカタログで代替すると誤った雛形が黙ってできるため、代替はしない。
  • dataName_*.csv 欠落時にパーツ名なしで全体が落ちる: DataName 軸の結合だけ存在確認をせずに読んでいたため、polars の FileNotFoundError がパーツ名の名指しなしで漏れていた → parameterLabel_ 側と同じ「解決できない軸」の軸名つきエラーに axis_resolve.py:102-110。
  • 分母事前集計の追加で例外: 軸カタログが空のパーツ(設定のみ編集)で「+ 事前集計を追加」を押すと min() が空列で落ちていた → 無効化 widgets.py:855-859。
  • introspect が .csv.gz を見ない非対称: エンジン・バッチは gz を直読みできるのに、UI の type 検出・軸カタログは .csv だけを探していた → data_file と同じ扱いで .csv.gz も対象に introspect.py:26-44。
  • 画面3・4だけの編集が自動保存されない: 保存条件に groupDefs / weightSets / constraintThreshold を追加 app.py:230-235。
