# 仕様変更ノート: 相対化のOverride判定廃止 → DataName / Measure番号指定へ

作成: 2026-07-24。担当者ヒアリング(2026-07-23〜24)の結果と実装方針の記録。
実装着手前のワーキングノート。実装完了後は docs/score_gui_design.md へ反映して本ノートは整理する。

## 1. 判明した事実(担当者ヒアリング)

- **相対化(分子/分母)の判定に Override の True/False は使えない**。
  現行の config_mini.jsonc 等にある `split_axis: "Read_Override"` +
  `numerator_when: true / denominator_when: false` という前提は旧仕様。
- 代替として、ユーザが map_dataName.csv の **DataName 値を分子/分母として選ぶ**操作になる。
  例: `0,reference_param_read_level_1` を分母、`1,evaluation_param_read_level_1` を分子。
- ただし DataName は実験者が**最適化実験前に VBA でパラメータ測定フロー
  (Program/Read/Erase の並び)を設計する際に自由につける**ものであり:
  - 命名ルールは未整備
  - **そもそも付けない場合がある**(→ 文字列で指定することすら不可能なケースが存在)
- 測定フローが Measure(測定順序番号)を決める。フロー設計者は
  **どの Measure 番号がどの測定に当たるかを知っている**。
- 測定は1回あたり長くて20分程度かかる → 実データ到着後にエラーで気づく運用は手戻りが大きい。
- 事前情報の入手見込み:
  - **Measure の数**だけはスコア設計前に取得できるよう依頼する(担当者へ依頼済み/依頼予定)
  - それ以上の情報(実験設定から出力csvの要素を列挙する機能)は将来課題。時期未定
  - フローファイル自体は事前に存在するので、解析スクリプトが作られればいつかは情報化可能
- 出力されるファイル(type として選べるもの)すら不明な場合がありうる(未確定)。

## 2. 合意した設計判断

- **Measure 番号を第一級の識別軸に昇格させ、相対化・filter に使えるようにする**。
  dataName が無い実験では他に手段がなく、フロー設計者は番号の意味を知っているため成立する。
- **フローが変われば同じスコア設定は再利用できない — これは許容する**。
  スコア設定はそもそも特定フローに対して設計するもの。欠陥ではなく前提。
- 識別子の優先順位は「あるものを使う」:
  DataName あり → DataName(候補提示 or 自由記述)、無ければ Measure 番号。
  Measure 軸は必ず存在するので UI には常に出す。設定スキーマは全ケース共通。
- DataName の自由記述入力も可能にする(自由度向上として否定しない)。
- **検証の主軸を実行時から設計時に移す**(測定20分のコストのため):
  1. Measure 数による範囲チェック(設計中に即時)
  2. 合成データによる構造ドライラン(order/op/仮想ステップ/joinの構造エラー検出。数値検証は不可)
  3. 実行時の「候補列挙つきエラー」は最後の防衛線に格下げ
- 設定ファイルに想定 Measure 数等のメタ情報を持たせ、別フローのデータへ誤再利用したとき
  「黙って間違った数値が出る」事故を validate で警告する(存在する番号同士なら計算は通ってしまうため)。

## 4. 実装プラン(2026-07-28 改訂。9節の合意を反映)

- 同じ理由+二重指定回避のため、**Measure 軸のある type の雛形には
  parameterLabel 由来の Label/Override 軸を入れない**(明示追加は可能。
  Measure 番号がそれらを一意に決めるため)。
- 相対化ONの初期値は split 軸の候補から**位置**で選ぶ(先頭=分母、2番目=分子。
  Override の [False, True] では旧既定と一致)。命名ルールによるペア検出とは
  別物で、ルール確定後の第2弾で置き換わる。

2. **introspect**: axis_catalog に Measure 軸(Measure 列を持つ type のみ・実在値から)と
   DataName 軸を追加。ダミー一式にも実データにも同じ経路が働く。
3. **UI**: split軸候補の Override 限定を解除。分子/分母・filter の Measure 選択は

5. **validate モード**: CLI に「計算せず参照整合性だけ検査」を追加

   設計時はダミーでテストできるため、主用途は**測定後・本計算前の2段目の防衛線**
   (フロー改訂による番号ズレ、別フロー設定の誤再利用の検出)。

## 4.5 事前情報の優先順位と UI の適応方針(2026-07-24 追記)

**(2026-07-28 追記: 下記順位1のダミー一式が実現した — 9節。本節の縮退方針・
レベル分けは経緯として保存。)**

前提の追加: **typeファイルによっては既に集計済みで出力され、Measure 列が無いものもある**。

スコア設計前に入手できる情報の理想順位:

1. **実データと同形式のダミーファイル一式**(測定値のみダミー)が圧倒的第1希望。
   既存の introspect 経路にそのまま読ませるだけで候補表示・雛形・テスト計算(構造検証)が
   全部動き、「データなしモード」の縮退実装自体が不要になる。Measure 無しの集計済み type の
   変則スキーマも、ダミーが正として示してくれる。
2. ダミーが無理なら、**typeごとの列構成(スキーマ)込み・機械可読**の整理情報
   (Measure数・dataName一覧・軸一覧)。これがあれば、こちらでダミー生成器を書いて 1 を合成でき、
   実質 1 と同等。列構成を含まない一覧だけだと集計済み type に検証不能な穴が残る。
3. type 候補一覧(2に含まれるはず)。単独でも「作れるパーツ」の提示と参照エラーの設計時検出に使える。
4. チップ・ボード数は単独では価値が低い(大抵 mean/max で畳む軸)。2 と組み合わせて
   ダミー合成の形状情報として意味を持つ。

依頼の形: 「1 をもらえるなら他は不要。無理なら 2 をスキーマ込みで+形状情報。」

UI の適応方針: グローバルな「データあり/なしモード」の2分岐にせず、
**読み込めた情報から機能ごとに可否を導出**する(axis_catalog の「候補 or None=自由入力」
パターンの一般化)。
- 実データ/ダミーあり → 全機能。ダミー時はテスト結果に「数値は無意味、構造検証のみ」と明記
- スキーマ+形状あり → 候補表示・validate 可。テストは内部でダミー合成して「合成データによる構造テスト」
- type一覧のみ/なし → 自由入力。テストボタンは **disabled + 理由文言**
  (非表示より「何を用意すれば押せるか」を案内できる方を推奨)

## 4.6 出力側との取り決め: 欠測スロットの表現(2026-07-24 担当者相談への回答)

担当者からの相談: (i) Block ごとに Measure 回数が違ってよいか
(Block0 は Measure 0,1、Block1 は 0,1,2 等)。(ii) 存在しない測定のところに
負の値か NaN を入れようと思うが困るか。

回答(原則: **無いものは行ごと出力しない — 空やダミーで埋めない**):

- (i) **困らない**。出力csvは (Board, Chip, Block, ..., Measure) キーの行集合であり
  固定長配列ではないため、ラグ付きでそのまま成立する。filter/集計は存在する行だけを
  対象に正しく計算される。設計者への寄与範囲の可視化は被覆情報表示(実装プラン8)で支援。
- (ii) 詰め物は不要かつ有害。**負の値は絶対NG**: 実測値と区別不能で、mean/worst/percentile/
  相対化/dVtBudget(log10(負)→NaN、offset+1で log10(0)→-inf)を**エラーなしで静かに壊す**。
  「FBCは非負だから負=欠測」は差分系など負値が正当な type があり汎用規約にできない。
  **NaNも避けたい**: polars は null(空セル)を集計でスキップするが NaN は float として
  伝播し、1個のNaNがスコア全体を汚染する(読込時 NaN→null 変換で無害化は可能だが余計な防御層)。
  どうしても何か出力するなら**空セル(null)が次善**(集計が自動スキップ。ただし
  「測定したが値なし」と「未測定」が曖昧になる)。
  ラベル無し実験の「ファイルごと欠落に倒してほしい」(確認事項3)と同一原則。
- 補足: 旧方式の全展開(FBC_expanded 相当)でもラグ付きデータは問題ない。展開は
  (InBatchEpoch, Board, Chip, Block, Measure) キーの行ごと結合であり固定長配列ではない
  ため、無い測定は「行が無い」まま素通りし、穴も詰め物も発生しない。
  依頼は1行に集約できる: **実行した測定の行は全ファイル({type}.csv / parameterLabel /
  dataName)でキーを揃えて出力し、実行していない測定はどのファイルにも行を出力しない**
  ({type}.csv にだけ行があると旧スクリプトは空ラベル・新エンジンは null を黙って作るため)。

## 5. 担当者への確認事項(重要順)

1. 質問「Measure 番号は実験出力の全行(全ボード・チップ・ブロック・epoch)で同じ測定を
   指すと保証されるか。リトライ・条件分岐・ボード別フロー等でズレることはないか」
   → **解決済み(2026-07-24、ユーザ確認。担当者への質問は不要)**。
   **Measure はユーザが定義した個々の測定に紐づく番号**であり、出力はその番号のスロットに入る。
   実行順の連番ではないため、リトライ・失敗・スキップで他の番号がズレることは構造的に無い。
   別フロー(別の測定定義)なら別の Measure 番号になるため、ボードごとに走る測定が違っても
   「埋まっているスロットが違う」だけで、同じ番号が別の意味を持つ衝突は起きない。
   測定失敗・未実行の帰結は「実験ごとエラー」か「その番号が空(行が無い)」で、
   filter 0行 / join null として検出可能な良性の壊れ方 → validate とエラー改善で拾う。
   残る唯一の課題は正しさではなく**可視性**: ボードごとに測定が違う実験で Board worst 等を
   取ると「その Measure を持つボードの中での worst」になる。設定者がどのボードが寄与して
   いるかを理解できるよう、被覆情報表示(実装プラン8)で支援する。
2. 質問「事前取得できる Measure の数は type(FBC, tR, ...)ごとか全体で1つか。
   番号は0始まり連番か、欠番はありうるか」
   → **回答済み(2026-07-25)**: Measure 採番は type ごとではなく**実験全体で1つ**。
   0始まり連番・欠番なし。Measure 列自体が無い(集計済み)type はある。
   → カタログの measure_count / measures はトップレベルに置き、validate の範囲チェックは
   グローバル count で行う(6.2節に反映済み)。
3. 質問「ラベル・dataName 無し実験では parameterLabel_*/dataName_*/map_* は
   欠落するのか、空で出るのか、一部のみ命名か(縮退パターンで実装とテストが決まる)」
   → **対応方針確定(2026-07-25)**: 「欠落にしてほしい」と依頼できるとのこと。
   依頼内容は 7 節「担当者への依頼事項まとめ」に集約した。
4. type の事前把握: ダミー一式で解決(9節。旧カタログ案は廃止)。
   小確認も **2026-07-28 に全て解消**:
   (a) ファイル命名規約({type}.csv / parameterLabel_{type}.csv / dataName_{type}.csv /
       map_*.csv)→ **維持を要求可能**。正式依頼に昇格(7節5項)
   (b) map_*.csv の要素候補の正 → ダミー一式に map_* が含まれるため**ダミーが正**。解消
   (c) type 名 → **ユーザ定義**(測定返り値の numpy 配列を DataFrame へ整形する担当者の
       スクリプトが命名。FBC も測定返り値では別名)。dVtBudget パーツが FBC.csv を
       焼き付けで読む実装のため、「FBC」名の維持を依頼して対応(7節5項)
   (d) → カタログ廃止により質問ごと消滅。ダミーは1 epoch 分で足りる
       (InBatchEpoch はもともと集計対象外の軸)
4b. 質問「Measure 列の無い集計済み type では基準パラ/評価パラを区別する列は何か
   (存在するのか)。無ければ相対化不可として扱う必要があるのでは」
   → **回答済み(2026-07-25)**: Measure 無し=既に集計済みの type に基準/評価の識別列は
   無い。相対化そのものはせず、似た演算は Chip 番号等での割り算・引き算で足りる。
   → エンジンの relative は既に軸汎用なので、UI で split_axis をその type の任意軸から
   選べるようにすれば対応完了(相対化プリセットは OFF)。列構成はカタログの axes で判明。
4c. 質問「実データと同形式・値のみダミーのファイル一式を実験側で生成してもらえるか」

5b. 質問「dataName と Measure は 1:1 か。同じ dataName が複数 Measure に付くことはあるか」

## 6. データ入力とUI適応の詳細設計(2026-07-25、担当者回答を受けて)

担当者の確約: フロー解析により **どのファイルが出力されるか+Measure数**(これが無いと
まともなUIにならないため必須で対応)+**各ファイルの軸**を出力する。
dataName は現時点でユーザ任意(最初期は担当者付与フローなので有り)、将来は自動付与方針。
Board/Chip 数などはフローが知り得ないので別ソースから。

### 6.1 内部表現: Measure が実行の正、dataName は表示・検証層

- UI で dataName を選んでも、**設計時にカタログで Measure 番号へ解決して保存**。
  dataName 文字列は `labels` 注記として併記(UI表示と validate 照合用、実行には不使用):
  `"relative": {"split_axis": "Measure", "numerator_when": 1, "denominator_when": 0,
  "labels": {"1": "evaluation_...", "0": "reference_..."}}`
- 実行時は常に Measure 番号のみ(実行経路1本。dataName が出力に無くても同じ設定で動く)。
- validate で「Measure 1 の dataName は今も evaluation_... か」を照合し、
  フロー改訂による番号ズレを警告。dataName の意味安定性は検証系で活かす。
- 手動 Measure 指定時もユーザが `labels` にメモを書けるようにし、番号の属人化を緩和。

### 6.2 受け渡し形式: カタログ jsonc(仮csvではなく)

**(2026-07-28 廃止: ダミー一式方式へ転換 — 9節。「フローが知らない Board/Chip」問題は
担当者側の「Board/Chip は1つで出力し UI 側で複製展開」案で解決した。以下は経緯として保存。)**

仮のダミーcsvはフローが知らない形状(Board/Chip数)を要求するため受け渡し形式にしない。
「フローが知っていることだけ書ける」カタログを定義し、ダミーはこちらが合成する。
**Measure 採番は実験全体で1つ**(2026-07-25回答: type別ではない・0始まり連番・欠番なし。
Measure 列自体が無い type はある)ため、measures はトップレベルに置く:

```jsonc
{
  "catalog_version": 1,
  "measure_count": 12,           // 必須。実験全体で1つ(0始まり連番・欠番なし)
  "measures": [                   // 任意: dataName対応。1:多がありうるので全行列挙
    {"measure": 0, "dataName": "reference_param_read_level_1"},
    {"measure": 1, "dataName": "evaluation_param_read_level_1"}
  ],
  "types": {
    "FBC": {"axes": ["WL","STR","State","Board","Chip","Block"],   // 必須(確約済み)
             "has_measure": true,
             "measures": [0, 1, 3]},                                // 任意: このtypeに現れる番号
    "SUMMARY_X": {"axes": ["Board","Chip"], "has_measure": false}   // 集計済みtype
  },
  "axis_values": {"State": ["R2A","A2R","A2B","B2A"]}    // 任意(map_*は共有なのでtype共通)
}
```

**VBA からの出力は csv になる可能性がある**(2026-07-25回答)ため、同内容のフラット csv 群
(catalog_meta.csv: measure_count 等 / catalog_types.csv: type,has_measure /
catalog_axes.csv: type,axis / catalog_measures.csv: measure,dataName空可 /
catalog_axis_values.csv: axis,value)も等価形式として定義し、ローダで同一内部モデルに
正規化する。jsonc と csv 群のどちらで来ても同じ。

**数だけの情報(WL本数・Chip数等)の受け方**: 「数」は「要素一覧」の圧縮表現
(番号0始まりなので count N = 要素 0..N-1)。カタログに `axis_counts` セクションを設け、
数しか持たないソースは **counts だけの部分カタログ**を出せばよい:
`{"catalog_version": 1, "axis_counts": {"Board": 4, "Chip": 4, "Block": 2}}`
(csv版: catalog_axis_counts.csv = axis,count)。
WL本数・STR数は既存の {Generation}.json(numWLs, numStrings)が既にこの情報源なので
新ファイル不要 — ローダが同じ内部形式へ写す。Board/Chip 数はファイル化されるまで UI 手入力。

**結合方法**: DataFrame join ではなく、UI がカタログを組み立てる時点の
**軸名をキーにした辞書マージ**。
1. 各ソースを「(type, 軸) → 要素情報」に正規化。要素情報は `values`(明示列挙) /
   `count`(0..N-1 扱い) / なし(自由入力) のいずれか。軸一覧は type スコープ、
   要素・count は軸名スコープ(Board は type 横断で共有)
2. 軸名キーで重ね合わせ。`values` > `count`(情報量で優先)、同種の矛盾は出所つき警告
3. 使う側は統合後だけを見る: filter 候補は values→ドロップダウン / count→範囲チェック付き
   数値入力(WL 0..1583 をドロップダウンにはしない)。合成テストの形状と validate の
   範囲チェックは count を使う

ソースの別(フロー解析カタログ / 世代情報 / 形状カタログ / 手入力 / 実データ /
過去の同世代実験からの要素借用)とUIの使い方はこのマージで完全に分離され、
ソースが増えても規則は不変。形状情報は合成テストにだけ必要で候補表示には不要 —
欠けていても L1 テストは可能。

### 6.3 情報レベル別の UI・テスト可否

**(2026-07-28 廃止: ダミー一式で常に L3 相当になるためレベル分岐は不要。
「ダミー時はテスト結果に『数値は無意味、構造検証のみ』と明記」だけ存続 — プラン4。)**

**確約された最低ライン(type+Measure数+軸)だけで構造テストは可能**。
構造検証は Board1×Chip1×Block1×WL数点の最小合成データで足り、未知の数値軸は2〜3値、
WL数は世代情報から取得(WLgroup検証も可)。

| レベル | 情報 | 要素入力 | validate | テスト |
|---|---|---|---|---|
| L0 | なし | 自由入力 | 構文のみ | 不可(disabled+理由) |
| L1 | カタログ最低ライン | type選択・Measure範囲つき数値・他自由 | type/Measure範囲/軸名 | 可(最小合成・構造のみ) |
| L2 | +dataName一覧 | dataNameドロップダウン(=Measure表示) | +dataName照合 | 可(相対化ペア整合まで) |
| L3 | +軸の要素候補 / 実・ダミーデータ | 全選択式 | 全項目 | 可(実データなら数値確認も) |

実装は「モード分岐せず機能ごとに可否導出」(4.5節)。type ごとに情報レベルが違う
中間状態も軸単位マージで自然に扱う。

### 6.4 Measure 番号の UI 表示方針(2026-07-25)

これまで Measure は結合キー専用で UI に出していなかった(axis_resolve が drop、
カタログにも無し)が、識別子に昇格したため表示に出す:

- dataName が分かる場合は**複合表示「evaluation_... (Measure 1)」**を基本にする
  (保存は Measure 番号、表示は dataName 優先)
- dataName が無い場合は「Measure 2」+ ユーザメモ(labels 注記)を表示
- 表示箇所: filter 候補、相対化の分子/分母選択、被覆情報、validate メッセージ、
  パーツ一覧のサマリ
- 生番号の直接入力も常に可能(measure_count による範囲チェック付き)
- **1:多 dataName**(ループ内複数測定。2026-07-25 回答で存在確認)は
  「dataName (Measure 3,4,5)」と全番号を見せる。v1 では filter は is_in 可、
  相対化は単一番号をユーザに選ばせる(複数測定の集約 — 分子側は複製として後段集計に
  流せるが分母側は join 重複のため事前集約が要る — は将来拡張)
- Measure 列の無い(集計済み)type では Measure を表示しない。相対化は split_axis を
  その type の任意軸(Chip 等)から選ぶ形で許可(エンジンは既に軸汎用。4b 回答:
  識別列は無く、Chip 番号等での割り算・引き算ができれば良い)

### 6.5 マージの実例(2026-07-25 合意済み)

**(2026-07-28 廃止: 4ソースマージ・借用・競合優先順位はダミー一式方式で不要に — 9節。
ただし本節末尾の「Measure 選択 UI の実体は常に Measure の一覧」という表示方針は
6.4節とともに存続する。)**

入力4ソース:
1. **flow_catalog.jsonc**(今回のフローの解析結果): measure_count 4、measures
   (0:reference_param_read_level_1, 1:evaluation_param_read_level_1,
   2:reference_param_read_level_2, 3:dataName無し)、
   types = FBC{WL,STR,State,Board,Chip,Block / has_measure:true},
   tR{WL,STR,Page,... / has_measure:true}, PROGSUM{Board,Chip / has_measure:false}。
   State/Page の要素はフローが知らないので書かれない。
   ※「一部の測定だけ dataName 無し」の混在がありうるかは仮定・要確認(確認事項5c)。
   どちらでも設計は壊れない(名無しは番号表示になるだけ)。
2. **B9LS.json**(世代情報・従来のまま): numWLs 6, numStrings 4
   → ローダが WL: count 6 / STR: count 4 に写す
3. **shape_catalog.jsonc**(形状部分カタログ): {"axis_counts": {"Board":2,"Chip":2,"Block":2}}
4. **過去の同世代実験dir**(借用指定): map_State.csv → State 要素、map_Page.csv → Page 要素。
   **借用は世代で固定される軸(map ファイル由来のデバイス特性)に限定**。
   Measure・dataName などフロー依存情報の借用は禁止(過去フローの番号・名前は今回と無関係)。

統合カタログ(FBC を開いたとき):

| 軸 | 要素情報 | 出所 | UI |
|---|---|---|---|
| Measure | count 4 + dataName対応 | フローカタログ | Measure一覧リスト(下記)+生番号入力(範囲0..3) |
| State | values R2A/A2R/A2B/B2A | 過去実験(借用表示) | ドロップダウン |
| WL / STR | count 6 / 4 | 世代情報 | 数値入力(範囲)。WLgroup 検証にも使用 |
| Board/Chip/Block | count 2 | 形状カタログ | 数値入力(範囲0..1) |

tR は State→Page(借用 L/M/U)、PROGSUM は Board/Chip のみ・Measure 行なし
(相対化の split_axis 候補 = Board/Chip)。マージキーは軸名なので Board の形状は
全 type に一度で効く。この時点で候補提示・範囲 validate・合成構造テストまで可能
(= 測定前に設定を書き切れる)。

**Measure 選択 UI の実体は常に「Measure の一覧」**で、dataName は行の表示名として
付いたり付かなかったりするだけ(入力方式が2つに分かれるのではない):

```
分子側の選択:
  reference_param_read_level_1   (Measure 0)
  evaluation_param_read_level_1  (Measure 1)
  reference_param_read_level_2   (Measure 2)
  Measure 3  (dataName無し)          ← 名無しもリストから漏れない
```

どれを選んでも保存は Measure 番号。名無し選択時はユーザメモ(labels 注記)欄を出す。
validate は名前付き = 番号↔dataName の一致まで照合、名無し = 範囲チェックのみ。

**競合時の優先順位**:

> 今回の実験の測定データ(観測) > 今回のフロー由来カタログ(予測) > 形状・世代情報
> > 過去実験からの借用(参考。世代固定軸のみ)。加えて values(明示列挙) > count(数だけ)。

- **設計時(測定前)には「今回の測定データ」は存在せず最上位は空** — 設計は予測のみで行う。
  この規則は設計前〜測定後までを1つの規則で通すためのもので、各時点では存在する
  ソースだけが効く。
- 「今回の測定データ」が登場するのは設計後のライフサイクル:
  (a) 測定後の validate(実行前に設定と実データの整合を検査する2段目の防衛線)
  (b) 実験途中・実験後に UI を再度開くとき(バッチで epoch ごとにデータが溜まる中での
  結果確認・原因調査・次バッチへの設定修正)。
  なお**スコア計算そのものは統合カタログを見ない** — 計算は常にデータファイル自身に
  対して走る。統合カタログは設計・検証支援の仕組み。
- 観測が届いたら観測が予測に勝つ理由: 候補・validate の目的は「計算が実際に見るものを
  設計者に見せる」こと。カタログ側を優先すると、実在する要素(例: 形状カタログは
  Board 2個宣言だが実データに Board 0..3)が「範囲外」と誤判定され、計算対象に
  存在するものを設定できなくなる。
- 矛盾の警告は残す — ズレは「形状情報が古い」か「実験が設計どおり走らなかった」かの
  診断情報: 「⚠ Board: 実データ4要素(0..3)、shape_catalog.jsonc は 2 と宣言。実データを採用」
- 過去実験の借用が最下位の理由は逆: 過去実験は設定が違う可能性があり、今回のフロー由来
  情報より常に古い。フローカタログが将来 State の要素まで出せるようになれば、
  借用は警告なしに置き換わる(ソースが賢くなるほど借用・手入力が不要になる)。

### 9.1 追加の確定事実と世代情報 json の扱い(2026-07-28)

- **WL/STR 等の本数は世代で固定。測定フローが一部の WL だけ測る設定は存在しない**
  (担当者=ユーザ確認)。上位 WL の行が欠けるような壊れ方も起こらず、
  起これば測定時に落ちる。→ データ(ダミー一式含む)の最大値+1 が軸の総数として
  常に正確。
- この帰結として **{Generation}.json(世代情報)は必須でなくなった**:
  - UI: 入力欄を廃止(「スコア計算を知らないユーザ向けに簡潔な UI。使わない項目は
    混乱を招くので残さない」というユーザ方針)。本数整合チェックはデータ由来
    (data_axis_counts)で常時実行され、世代情報が無いと警告がスキップされる
    従来の穴も塞がった。ディレクトリ内に json があれば自動検出し、データ由来と
    食い違うときの診断警告にだけ使う(観測 > 宣言)。
  - エンジン: Physical 記法の軸総数 N は json があればそこから(互換優先)、
    無ければ測定csvから導出(cli.derive_axis_counts)。CLI 引数 --generation-info は
    互換のため残る。
- Board/Chip 数だけは引き続きデータから分からない(フローが知らない軸)ため、
  ダミー展開時の手入力が唯一の情報源のまま。
